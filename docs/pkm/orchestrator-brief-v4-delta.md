## A. Продуктовая модель: единая поверхность + облако-карта

Две поверхности, строго разделённые по ролям:

**Board (стик).** Главная рабочая поверхность = открытая заметка в CodeMirror. Пользователь пишет как в sticky note. Всё эмерджентное происходит здесь, не выходя из текста:

- `#тег` подхватывается на лету (уже реализовано).
- `[[` вызывает автокомплит по заголовкам существующих заметок.
- `[[Несуществующее]]` создаёт frontier-ссылку; клик по ней предлагает создать заметку.
- Проза, содержащая заголовок существующей заметки, мягко подсвечивается как unlinked mention; один клик материализует её в `[[...]]`.
- Выделение текста → «Создать задачу» (v3 §8.3).
- Клик по task-ref открывает task drawer (см. §B.3).

**Cloud (карта).** Отражение всех данных: атомарное облако заметок, кластеризация тегами (гравитация), связи пружинами. Роль — навигация: быстрый переход к кластеру/теме, обзор задач в рамках темы, телепорт в конкретную заметку. Облако ничего не редактирует и не создаёт; это read-навигация.

Пространственный канвас со множеством стиков (Heptabase-style) в v1 не делаем. Решение можно пересмотреть после dogfooding.

## B. Дополнения к UX-контракту (расширяют v3 §8)

### B.1 `[[` автокомплит

- Триггер: ввод `[[` в редакторе.
- Список: заголовки существующих заметок, фильтр по подстроке (case-insensitive), максимум 8 подсказок.
- Accept: вставляет `[[Заголовок]]`.
- Ввод нового текста + accept «Создать»: вставляет `[[Новый заголовок]]` как frontier-ссылку (заметка НЕ создаётся автоматически).
- Клик по frontier-ссылке в тексте → action «Создать заметку „…"» → создаётся заметка с этим title, `note_links.target_note_id` проставляется при следующем reconcile.

### B.2 Unlinked mentions

Пассивное обнаружение связей. Правила детекции (в reconciler):

- Кандидат: вхождение заголовка существующей заметки в прозу текущей заметки.
- Сравнение: whole-word, case-insensitive; заголовки короче 3 символов игнорируются.
- Исключаются: fenced/inline code, уже существующие `[[...]]`, самоупоминание (title своей же заметки), строки task-ref.
- Результат: строка в `note_links` с `link_type='suggested'`, `raw_target` = заголовок, `target_note_id` = id найденной заметки.
- Suggested-строки — derived index: сбрасываются и пересобираются при reconcile так же, как wiki.

UX в редакторе:

- Mention подсвечивается пунктирным подчёркиванием (decoration, текст не меняется).
- Клик → два действия: «Связать» (материализовать в `[[...]]` через editor transaction) и «Скрыть» (dismiss).
- Dismiss персистентен (см. §C), после dismiss пара (заметка, target) больше не подсвечивается и не попадает в suggested-индекс.

Жёсткое правило (см. INV-9): машина никогда не переписывает прозу сама. Suggestion = подсветка + индекс. Изменение markdown — только явное действие пользователя.

### B.3 Task drawer

- Клик по task-ref widget в тексте → выдвижная панель (drawer справа на desktop, bottom sheet на mobile). Не модалка: текст заметки остаётся видимым.
- Содержимое v1: title (редактируемый), status toggle, deadline, urgency, список заметок с ref'ами этой задачи (клик → переход). Subtasks добавятся в M2.5 сюда же.
- Правки идут через TaskRepo и rewrite ref-строк по правилам v3 §8.5 (текущая строка сразу, остальные лениво).
- Из task pool клик по задаче открывает тот же drawer.

### B.4 Cloud view

Полная спецификация — в `worker-tasks/m-cloud-m-board-worker-tasks.md`. Контракт уровня продукта:

- Узел = заметка. Цвет = доминирующий тег, кольцо = второй тег, серый = без тегов.
- Layout = гибрид: гравитация тегов + пружины связей (wiki сильные, suggested слабые).
- Бейдж на узле = количество открытых задач в заметке.
- Клик по узлу → открыть заметку (Board). Клик по лейблу тега → подсветка кластера + переход к пулу задач с фильтром по тегу.
- Zoom/pan, hover-tooltip с заголовком, drag узлов (позиции не персистятся в v1).
- Облако read-only: не создаёт и не редактирует данные.

## C. Схема: миграция v2

Единственное добавление — персистентные dismissals для mentions (это user state, не derived index, поэтому отдельная таблица, а не флаг в `note_links`):

```sql
CREATE TABLE link_suggestion_dismissals (
  source_note_id TEXT NOT NULL REFERENCES notes(id) ON DELETE CASCADE,
  raw_target     TEXT NOT NULL,
  created_at     INTEGER NOT NULL,
  PRIMARY KEY (source_note_id, raw_target)
);
```

Reconciler при сборке suggested-индекса пропускает пары, присутствующие в dismissals. Переименование заметки-цели не воскрешает dismissal (ключ по `raw_target`): если title изменился — это новая пара, подсветка вернётся, что корректно.

Под облако новых таблиц не нужно: входы — существующие `notes`, `note_tags`, `note_links`, `task_refs`, `tasks.status`.

## D. Новые инварианты

- INV-9. Suggested links и любые механизмы автодетекции никогда не мутируют `notes.markdown`. Материализация — только явное действие пользователя через editor transaction.
- INV-10. Cloud view — производное отображение. Он читает через репозитории, ничего не пишет, не хранит собственного авторитетного состояния (layout-позиции эфемерны).

## F. Процесс (заменяет v3 §2 для этого проекта)

Гранулярность «воркер ≤6 файлов / ≤7 критериев» откалибрована под SCAFFOLD (зрелый код, дорогие регрессии) и на greenfield создаёт налог на декомпозицию. Для PKM до конца M-Polish:

- Единица работы = milestone-слайс, исполнитель = один агент (Claude Code) на слайс. Внутри спеки задачи остаются нарезанными (TB.x/TC.x) как чек-поинты самопроверки агента, а не как отдельные worker-чаты.
- Бриф v3 + эта дельта живут как контекст проекта (CLAUDE.md / прикреплённые доки).
- Инварианты переводятся из чеклиста ревьюера в автоматику: INV-5 — eslint `no-restricted-imports` (запрет импорта sqlite-модулей вне `src/storage`), INV-6/7 — уже покрыты тестами, INV-9 — unit-тест реконсайлера «markdown не изменился после rebuild». Ревью = прогон lint+test+build и просмотр диффа.
- Правило эскалации сохраняется: решение вне брифа/дельты → стоп и вопрос владельцу.

Возврат к мелкой воркер-нарезке — когда кодовая база станет достаточно дорогой, чтобы её беречь (ориентир: после первого месяца dogfooding).
